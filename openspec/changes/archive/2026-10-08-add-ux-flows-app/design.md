## Context

See `proposal.md` - "Why". Relevant constraints found while inspecting the repo:

- The monorepo is pnpm workspaces (`pnpm-workspace.yaml`: `apps/*`, `packages/*`), Biome for lint/format (`biome.json`, already globbed to `./apps/**/*`), TypeScript strict mode shared from root `tsconfig.json`, and `lefthook.yml` pre-commit hooks running `pnpm lint` / `pnpm check-types` repo-wide. A new app under `apps/*` is picked up by all of this with no config change.
- All three existing apps (`app-concepts`, `app-production`, `app-tellipod`) are Expo/React Native apps using Expo Router (file-based routing tied to Metro), Jotai for shared state, i18next/react-i18next for strings, and FSD (`app/entities/features/widgets/shared`) with `@/` path aliases. `app-concepts` additionally depends on `@mee/ui` (built on `react-native`/`react-native-web` primitives) and is the only app checked by Steiger (`pnpm steiger:concepts`), which enforces FSD layer boundaries.
- `openspec/config.yaml` already anticipates this app as `app-ux-flows: Vite web SPA`, distinct from the Expo apps. There is no existing Vite, plain-React, client-side-router, or Knip setup anywhere in the repo - this is new infrastructure, not a duplicate of anything existing. `lefthook.yml` has one stale, commented-out `knip: run: yarn knip` line from an earlier, never-finished attempt to adopt it; nothing in the repo runs Knip today.
- `@mee/ui` cannot be used as-is: it imports `react-native` primitives (`Pressable`, `Text`, `StyleSheet`) directly, not `react-native-web`-wrapped exports, so it only resolves inside an Expo/Metro + `react-native-web` toolchain, not a plain Vite + `react-dom` app.

## Goals / Non-Goals

**Goals:**
- Stand up `app-ux-flows` as a Vite + React + TypeScript SPA that fits the monorepo's existing tooling (pnpm, Biome, root `tsconfig.json`, root scripts) with no new root-level config.
- Define the Flow domain model, Flow Registry, Flow Runtime, and screen composition so that the behaviors in `specs/app-ux-flows/flow-runtime/spec.md` hold, and shape the seams (component resolution, flow configuration) so a later change can add variant overrides and analytics without reworking how flows are authored.
- Keep routing and page/business logic cleanly separated: route definitions resolve URL params and data, page components receive plain props and never touch the router directly.
- Reuse the state-management convention (Jotai) already established in `app-concepts`, and the i18next convention required by `CLAUDE.md`.

**Non-Goals:**
- A/B variant selection, assignment, or override application - the registry/config seam is shaped for it (see Decisions), but no variant logic ships in this change.
- Figma MCP-sourced components and Matomo analytics wiring - out of scope per the proposal; this design only notes where those would plug in.
- Reusing `@mee/ui` or adding `react-native-web` to `app-ux-flows` - rejected, see Decisions.
- A real, content-complete demo flow. This change ships one small example flow (two or three screens) whose only job is to exercise the registry/runtime/routing/completion path end to end; authoring real flows from Figma is future work.
- Steiger for `app-ux-flows`. Steiger enforces FSD layer boundaries (`app-concepts` is the only app that uses it); `app-ux-flows` uses vertical slices instead, so Steiger's rules don't apply. Knip (see Decision 6) is this app's structural/unused-code check instead.

## Decisions

**1. Vite + `react-dom` + TanStack Router, not Expo/Metro, not react-router.**
Expo Router's file-based routing is tied to the Metro bundler and React Native's navigation primitives; it buys nothing for a browser-only SPA and would drag in native-oriented tooling the app doesn't need. Vite is the de facto standard for a plain React SPA and needs no SSR/server runtime, matching "no SSR required." For routing, TanStack Router (`@tanstack/react-router`) is used: its `loader`/param-parsing model is what makes Decision 2's routing/page separation clean - a route declares how to parse its path params and load whatever data it needs, and only the route layer ever touches that mechanism. There is no existing client-side router in the repo to reuse, so this is a new dependency either way.
*Alternative considered*: `react-router`. It can be made to follow the same separation (resolve params in a route element, pass props down), but that separation has to be hand-rolled and isn't enforced by the library's own shape - TanStack Router's typed `loader` + `useParams`/`Route.useParams()` API makes "params and data resolution happen in the route, not the page" the natural way to write a route, not a convention someone has to remember.
*Sub-decision*: use TanStack Router's **code-based** route API (`createRootRoute`/`createRoute`/`createRouter`, routes declared as plain TypeScript objects) rather than its file-based route generator. The file-based generator needs `@tanstack/router-plugin`, a Vite plugin, and a generated `routeTree.gen.ts` watched/regenerated on every route change - overhead this app's handful of routes (home, flow, flow screen) doesn't need. Code-based routing keeps the toolchain to "Vite + one router package," matching "prefer the simplest architecture."

**2. Routing/page separation: thin routes in `src/routes`, plain-prop page components in `src/slices/*`.**
Each route is a small component whose only job is: parse/validate its path params (TanStack Router's `params.parse`), run a `loader` that resolves whatever data the page needs (e.g. look up a `Flow` by id in the registry, seed/read a flow instance), and render the corresponding slice's page component, passing the resolved params and loader data as plain props. Page components in `src/slices/*` take those props and nothing else - they never call `Route.useParams()`, `useLoaderData()`, `useNavigate()`, or import `@tanstack/react-router` at all. The one place a page needs to trigger navigation (advancing to the next screen, or to the completion view) is handled the same way: the route passes a `navigateToScreen(screenId: string): void` callback prop (which closes over the route's own `useNavigate()`) into the page component; the page calls that prop after updating flow state, instead of navigating itself.
- `src/routes/home.ts`: no params/loader; renders `slices/home`'s `HomePage`, passing the flow list (via the flow slice's registry read, called from the route) as a prop.
- `src/routes/flow.ts` (`/$flowId`) and `src/routes/flow.$screenId.ts` (`/$flowId/$screenId`): parse `flowId`/`screenId`, loader resolves the `Flow` from the registry (throwing TanStack Router's `notFound()` for an unknown id, satisfying "Registry resolves an unknown flow id") and resolves/seeds the flow instance; renders `slices/flow`'s `FlowPage` with `{ flow, instance, screenId, navigateToScreen }` as props.
This is a direct, testable rule: a page component's props are fully it needs to render and act; `grep -r "@tanstack/react-router" src/slices` should return nothing once this is followed.

**3. Vertical slice structure instead of FSD.**
`app-ux-flows` organizes code by feature, not by technical layer:
- `src/app/`: app-wide bootstrapping only - the entry point (`main.tsx`), i18n init, and mounting the router/root providers.
- `src/routes/`: the TanStack Router route tree (Decision 2) - routing and data-resolution wiring only, no UI beyond rendering a slice's page component.
- `src/slices/home/`: everything the home page needs (its `HomePage` component and any home-specific presentation logic).
- `src/slices/flow/`: everything flow-related end to end - the `Flow`/`FlowScreen` domain types, the Flow Registry, the Component Registry (Decision 4), the Flow Runtime state (Decision 5), and the `FlowPage`/screen-rendering/completion-view components. Flow behavior is one vertical slice because it is one cohesive concern; splitting it across cross-cutting "entities/features/widgets" layers (as FSD would) would scatter files that always change together.
- `src/shared/`: only code genuinely reused across more than one slice (none is needed yet beyond generic types/utilities, if any arise during implementation).
Each slice is free to organize its own internals (e.g. a `model.ts` plus a few components) without a repo-wide mandated sub-structure - that per-slice freedom, and the absence of cross-slice "may not import" layering rules, is why Steiger (an FSD-boundary linter) doesn't apply here (see Non-Goals) and Knip is used instead to catch unused code (Decision 6).

**4. Screens compose through a keyed Component Registry instead of each screen importing components directly.**
A screen definition is `{ component: <registry key>, props: <data for that component> }` (a screen MAY compose more than one such block). `src/slices/flow`'s component registry maps string keys to the actual React components used by flow screens. Rendering a screen means: look up each block's component by key in the registry, then render it with its props. This indirection is the concrete answer to "ensure the architecture can support variants cleanly later": a future variant layer only needs to intercept this one resolution step (to swap the key, patch the props, or skip the block) - flow authors and the runtime are unaffected. No variant-resolution code is added yet; only the registry-by-key indirection that makes adding it later a localized change. The registry lives inside the `flow` slice (not `shared/`) because, for now, only flow screens use it; promote it to `shared/` only if a second slice needs the same mechanism.
*Alternative considered*: screens as plain JSX/components composed directly (no registry). Rejected because later variant overrides (prop/copy/visibility/composition swaps "without duplicating the complete flow") would then have no single place to intercept composition without touching every flow or introducing wrapper components ad hoc.

**5. Flow Runtime state: one Jotai atom family keyed by flow id, persisted to `sessionStorage`.**
`src/slices/flow` keeps one active instance per flow id at a time (not per arbitrary "instance id" in the URL) - simpler than minting and threading instance ids, and sufficient for a demo/usability-testing tool where a participant runs one attempt of a given flow at a time. State is kept with Jotai's `atomWithStorage` (the `jotai/utils` equivalent of `app-concepts`' `makeAtomWithMMKV` pattern, backed by `sessionStorage` instead of MMKV) so that a page refresh mid-flow does not lose progress, while closing the tab clears it - consistent with "no backend required." A route's loader seeding/reading this state (Decision 2) means the atom read happens before the page component renders, not inside it. Starting a flow id that has no stored state (first visit, or a direct URL to an inner screen) seeds the atom from that flow's initial-data factory, satisfying the spec's "open a specific screen directly" scenario. Starting over after completion/abandonment re-seeds from the initial-data factory, satisfying "starting a flow again resets its state."
*Alternative considered*: a `Map<instanceId, state>` with instance ids carried in the URL, allowing multiple concurrent instances of the same flow. Rejected as unnecessary complexity for this MVP's participant-facing use case; the per-flow-id atom family already keeps different flows' state fully isolated, which is what the spec requires.

**6. Completion is a runtime status, not an authored screen.**
Each flow instance's state carries a `status: 'in-progress' | 'completed'` field (set by the runtime when the last screen's interaction completes) rather than the flow author adding a "completion" entry to the screen list. The `/$flowId/$screenId` route's loader resolves this status; `FlowPage` renders a generic completion view whenever `status === 'completed'`, regardless of which screen URL was visited - this directly satisfies "a completed instance is not re-entered as in-progress" without every flow needing to special-case its last screen.

**7. `@mee/ui` is not reused; no `react-native-web` dependency is added.**
Adding `react-native-web` solely to reuse `@mee/ui`'s one `Button` component would pull an entire RN-compatibility bundling layer into a plain Vite SPA for negligible reuse, and conflicts with keeping this app's toolchain simple. `app-ux-flows`'s Component Registry starts with small, local `react-dom` building blocks. If real duplication with `@mee/ui` grows later, extracting a web-targeted shared package is a separate, better-justified change.
*Alternative considered*: add `react-native-web` and depend on `@mee/ui` for visual consistency. Rejected for the reasons above; revisit if/when design tokens or multiple components need sharing.

**8. User-facing strings go through i18next, per `CLAUDE.md`.**
`app-ux-flows` adds `i18next`/`react-i18next` and a minimal single-locale (`en`) resource set, initialized in `src/app/i18n.ts`, mirroring `app-concepts`'s convention at a scale appropriate for a small internal tool (no ICU plural rules or device-locale detection needed yet).

**9. `@mee/core` is not added as a dependency in this change.**
Nothing in `app-ux-flows` needs its current export (`sharedGreeting`) or any other existing `@mee/core` utility yet. Adding the dependency now with no real import would be an unused, placeholder wire-up; it can be added via `workspace:*` the moment a shared, framework-agnostic utility is actually needed.

**10. Knip is added app-scoped only; Biome needs no new configuration.**
Biome already lints/formats `app-ux-flows` with zero new setup, because `biome.json`'s `files.includes` already globs `./apps/**/*`. Knip (unused files/exports/dependencies) is genuinely new - nothing else in the repo runs it today (only a stale, commented-out `lefthook.yml` line references it). `app-ux-flows` gets its own `knip.json` and a `knip` script in its own `package.json` (`pnpm --filter app-ux-flows knip`), scoped to that workspace only. It is deliberately not added as a root `knip.json` covering the whole monorepo, and not wired into `lefthook.yml`'s `pre-commit`: configuring Knip correctly for the existing Expo/React Native apps (entry points, dynamic requires, native-module side effects) is a separate, larger effort unrelated to shipping this app, and this change should not expand root-level tooling to do it. This mirrors the existing precedent that structural checks can be app-scoped (Steiger today runs only for `app-concepts`, via `pnpm steiger:concepts`, not repo-wide).

## Risks / Trade-offs

- [Path aliases (`@/app`, `@/routes`, `@/slices`, `@/shared`) are declared twice - once in `tsconfig.json`, once in `vite.config.ts` - and can drift] → Same pattern already exists between `tsconfig.json` and `metro.config.js` in the Expo apps; keep the alias list short and rely on `pnpm check-types` to catch drift (a bad alias breaks the type check immediately).
- [`sessionStorage`-backed runtime state means a participant loses progress if they close the tab or switch browsers, and two tabs on the same flow id will fight over the same stored state] → Acceptable for an internal demo/usability-testing tool; revisit (e.g. per-tab instance ids) only if real usage shows it's a problem.
- [The Component Registry's string-keyed lookup trades some type safety for the indirection variants need] → Keep registry keys as a generated union type derived from the registry object (`keyof typeof registry`) so a typo in a flow definition is still a compile-time error, not a runtime miss.
- [`app-ux-flows` is now the only app using TanStack Router, vertical slices, and Knip, while the three Expo apps use Expo Router, FSD, and Steiger] → Intentional and scoped: `app-ux-flows` is explicitly a different kind of app (browser SPA, no native target, no file-based routing); the proposal and `openspec/config.yaml` already record this split per app. The routing/page separation rule (Decision 2) and the one-vertical-slice-per-concern rule (Decision 3) are the local conventions that keep this app coherent on its own terms.
- [Knip needs its own per-app config and nobody in the repo has tuned one before] → Start with Knip's defaults plus only the entry-point override Vite SPAs typically need (`src/main.tsx`); expect to add ignore rules as false positives show up during task 1's verification, rather than pre-guessing them.

## Migration Plan

Purely additive - no existing app, package, or script changes behavior:
1. Scaffold `apps/app-ux-flows` (Vite + React + TS template), add it to root quality scripts implicitly via the existing `apps/*`/`packages/**/*` globs in `biome.json` and the `pnpm -r` fan-out in `check-types`. Add its own `knip.json` and `knip` script, scoped to the workspace.
2. Add one root script (e.g. `ux-flows:dev`) to run the dev server from the repo root, matching the `*:ios`/`*:android` naming convention used for the other apps.
3. Build the Flow domain model, registry, runtime, routing, and the one example flow per the spec.
4. Rollback, if needed, is deleting `apps/app-ux-flows` and the one added root script - no other workspace references it.
